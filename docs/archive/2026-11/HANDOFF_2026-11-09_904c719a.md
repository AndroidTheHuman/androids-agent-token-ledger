## Judgment calls

- **The brief's `session` in the sample hashes** → unit indexes restart in each transcript, so a sub-agent transcript is keyed `<session>/<agent file>` and a main transcript by the bare id (`transcriptKey`).
- **Units with 0 characters** → left out of the pool: they add nothing to the context, so there is nothing to code, and they carry no weight in attribution.
- **The sample's `unit` ids** → 1…180 in sample order, not the transcript index, so the coder gets no location hint. A rerun of `sample` traces them back.
- **A tool_result's `input`** → its tool_use's input, so the coder can apply the table's tool-based rows to results.
- **How `sample` gets text** → an opt-in callback in `extract` (one walk, the same unit numbers), not a second walker; it throws if a re-read unit's code or characters differ from the cache.
- **"§6's code table" in the coder's prompt** → the verbatim prompt, then §6's two Codes sentences, then §5's table with its lead-in line, minus BASE, THINK and COMPACT.
- **The five-project cap** (owner: "make sure this doesn't endlessly grow") → one unknown folder joins on its own. With two or more, none joins and the owner picks, so the tool never chooses.
- **`cleanupPeriodDays` value** → 365 (the owner said extend and decide later); one setting to change if disk use matters.
- **Reading the disagreements after the scores** → read-only, so part C can explain them; nothing re-coded or re-tuned, as §6 requires.
